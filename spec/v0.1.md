# HumanGrant Protocol 0.1 Draft

**Status:** local, unpublished draft. No RFC, OAuth, or product compatibility certification is claimed.

HumanGrant establishes an account-to-agent authorization relationship. It does not prove biological
human presence. An agent acts as itself, with an identified account's permission. Existing human
accounts and login methods remain in place. An email address is a notification destination, not an
identity. No external account, wallet, blockchain, or OAuth provider is required.

## 1. Terms and authority

MUST, MUST NOT, and SHOULD express requirements of this draft, not an IETF standard.
An **actor** is the public-key identity that initiated a request. A **grantor** is a stable,
server-authenticated account. The **client** is a configured application, not an identity assertion.
A **permission** is an exact `{action, resource}` pair within one configured target service.
The reference application defines `notes.read` and `notes.write`; unknown actions fail closed.
There are no wildcards, cross-service tokens, delegation, refresh tokens, or automatic renewals.

Effective authority is the intersection of requested pairs, explicitly approved pairs, the grantor's
current grantable pairs, current resource ownership, and current service policy. The business service
MUST check this on every operation, together with actor, client, service, expiration, and revocation.
Revocation and a business operation are serialized in one database transaction. An operation that
committed before revocation may finish; one ordered after revocation MUST fail.

## 2. Transport and representations

All endpoints use the configured origin. Production public origins MUST use HTTPS. This reference
HTTP listener binds to loopback and is placed behind a trusted TLS reverse proxy. Plain HTTP is
permitted only with explicit local-development configuration and a loopback public origin.
Forwarded headers, Host, arbitrary redirects, and client-supplied callback URLs are not trusted.
The proxy MUST preserve the exact method, path, body, and signed headers. It must impose connection,
body-read, and header timeouts. The reference implementation treats the direct peer as the source;
behind a proxy, that source limit is shared. It does not trust X-Forwarded-For.

Bodies are UTF-8 JSON, maximum 16 KiB. Unknown input fields are rejected. GET bodies are empty.
Protocol routes do not accept query strings or percent-encoded paths. IDs use ASCII safe tokens.
Timestamps are UTC Unix seconds (integer), not milliseconds. The time authority is the server.
Responses have `Cache-Control: no-store`, `Pragma: no-cache`, `Referrer-Policy: no-referrer`, and
`X-Content-Type-Options: nosniff`. Credentials NEVER appear in URLs or ordinary logs.

`GET /v1/requests/{id}/status.md` returns actual `text/markdown; charset=utf-8`, not HTML or JavaScript.
`GET /v1/requests/{id}` returns the same State object as JSON. Markdown serializes each stable field
as a JSON literal on its own line, so strings remain data, not instructions. Human notices and agent
instructions come from fixed templates. Requester-controlled purpose text is never interpolated
into operational instructions. Markdown does not refresh itself; clients make new signed reads.

## 3. Objects and lifecycle

A request binds request ID, actor public-key fingerprint, original public key, configured client,
target service, purpose (untrusted data), exact requested permissions, optional expected_human_id,
creation time, request expiry, and maximum grant expiry. These fields are immutable after creation.
Increasing authority requires a new request and new human consent.

| phase | status | status_text | Allowed next phases |
|---|---|---|---|
| waiting_human | waiting | 等待人类中 | authenticating_human, awaiting_consent, rejected, cancelled, expired |
| authenticating_human | human_login | 人类登录中 | awaiting_consent, rejected, cancelled, expired |
| awaiting_consent | human_login | 人类登录中 | approved, rejected, cancelled, expired |
| approved | human_login | 人类登录中 | succeeded, cancelled, expired |
| succeeded | success | 登录成功 | none |
| rejected | rejected | 已拒绝 | none |
| expired | expired | 已过期 | none |
| cancelled | cancelled | 已取消 | none |

`approved` means approved, awaiting the original AI's credential claim. Only `succeeded` means an
independent AI session exists. The status of a historical request and the current validity of its
grant are separate. `grant_status` is informational; `/v1/session` and each business operation
perform live checks. Expiry is resolved on each request transaction. `status_updated_at` changes
only when phase changes. `checked_at` is the current read time. Email and poll bookkeeping do not
change `status_updated_at`. A normal link GET cannot authenticate, approve, reject, or consume consent.

State fields: `protocol_version`, `request_id`, `status`, `status_text`, `phase`, `created_at`,
`status_updated_at`, `checked_at`, `expires_at`, `poll_after_seconds`, `human_authorization_url`,
`requested_permissions`, `email_request_status`, `email_retry_after_seconds`. Additional fields
include `forwarding_prompt`, `target_service`, `client_id`, `grant_id`, `grant_status`, and
`grant_expires_at`. See [field schemas](../schemas/protocol.json) and [OpenAPI](../openapi.yaml).

## 4. Public interfaces

| Method | Path | Caller and purpose |
|---|---|---|
| GET | /.well-known/humangrant.json | Public machine-readable discovery; no authentication |
| GET | / | Same discovery by default; optional reference agent UI |
| POST | /v1/requests | Signed AI; create an immutable request |
| GET | /v1/requests/{id} | Original signed AI; JSON state |
| GET | /v1/requests/{id}/status.md | Original signed AI; Markdown state |
| POST | /v1/requests/{id}/email | Original signed AI; fixed-template invite |
| POST | /v1/requests/{id}/claim | Original signed AI; one-time credential issuance |
| POST | /v1/requests/{id}/cancel | Original signed AI; cancel unfinished request |
| GET | /human/{link} | Anyone with the link; read-only review, no authentication proof |
| POST | /human/{link}/begin | Same-origin browser + CSRF; start identity verification |
| POST | /human/{link}/verify | Same browser + CSRF + challenge signature; verify account |
| POST | /human/{link}/approve | Verified same browser + CSRF; explicit scoped consent |
| POST | /human/{link}/reject | Verified same browser + CSRF; refuse consent |
| GET | /human/grants | Authenticated human browser; list own grants |
| POST | /human/grants/{id}/revoke | Same human browser + CSRF; revoke own grant |
| GET | /v1/human/grants | Signed, registered human key; list own grants |
| POST | /v1/human/grants/{id}/revoke | Signed, registered human key; revoke own grant |
| GET | /invite/{token} | Read-only mail refusal/block page |
| POST | /invite/{token}/reject | Same-origin browser + CSRF + mail action token; refuse only |
| POST | /invite/{token}/block | Same checks; refuse and suppress all future invites to this destination |
| GET | /v1/session | Signed AI + separate access credential; live actor/grantor/effective pairs |
| GET/PUT | /v1/notes/{id} | Signed AI credential or registered signed human; exact business check |

The human link, private state path, and claim path have distinct roles and values. A human link has
no credential-claim authority. The mail action token has refusal authority only, never approval.
A human browser cannot grant by GET. Browser write endpoints require an exact configured Origin,
a SameSite=Lax/HttpOnly session cookie, and a session-bound CSRF token. Cookies rotate at login.
Expected-human restrictions apply both during verification and consent. Without one, the confirmation
page clearly identifies the actual authenticated account that will grant access.

The public Rust `HumanAuthenticator` interface verifies host-controlled authentication evidence and
returns a principal. The reference `PublicKeyAuthenticator` verifies an expiring, one-use challenge
with an administrator-provisioned account public key. HTTP never accepts an arbitrary user_id as
login evidence. An integration adapter belongs in the trusted server, not in an agent prompt.

### Discovery and default headless operation

`GET /.well-known/humangrant.json` is public and returns the `Discovery` JSON object:
`protocol_version`, `origin`, `request_endpoint`, `session_endpoint`, `specification_url`,
`openapi_url`, `schema_url`, and `agent_ui`. All endpoint and document URLs are absolute,
constructed from the configured public origin, never from Host or forwarded headers.
`agent_ui` indicates whether the optional reference agent homepage is enabled.

The reference server defaults to `agent_ui: false`: `GET /` returns the same JSON without
rendering an agent interface. Explicit `agent_ui: true` enables the reference HTML homepage;
the well-known JSON endpoint remains available. Integrations SHOULD default to API discovery
without adding a visible application button. No behavior depends on User-Agent. This controls
presentation, not who can read public metadata; a human can also read the JSON.

Clients MUST establish the trusted origin independently before using discovered URLs. Discovery
is metadata, not authentication or permission. Signed APIs retain their signature requirements.
Human review, explicit consent, refusal, grant management and revocation remain available;
opening discovery or a human link MUST NOT issue a credential or silently approve access.

### Existing human login

A valid, server-verified login MUST lead directly to the permission confirmation view. Only a
missing, expired or invalid login requires authentication. Integrations MUST use the host's actual
session validator, not a posted account ID or an agent's assertion. The reference uses
`HumanAuthenticator::session_principal`; the host override is rechecked on every human operation.

An authenticated GET can display the account and choices, but MUST NOT advance the request phase,
approve access or create an AI session. The explicit approve/reject POST revalidates the login and
expected account, then enters `awaiting_consent` and applies the decision in one transaction.
No extra user click or authentication challenge is needed for this internal transition.
An invalid decision rolls back the transition. Request status remains distinct from page readiness.

Consent CSRF tokens are HMAC-SHA256 over the UTF-8 JSON array
`["HumanGrant browser action 0.1", ["consent", request_id, account_id]]`, keyed by the browser
session's server-side CSRF secret. They bind this browser, the displayed account and the immutable
request. Tokens for grant management and mail preferences use separate contexts. Switching account
or request invalidates the old confirmation. All POSTs still require the exact trusted Origin.
The reference cookie uses SameSite=Lax so a normal top-level link from email can carry an existing
login; cross-site submissions do not gain permission. Opening links does not extend the login's
30-minute server-side expiry. Integration hosts keep their own login lifetime and cookie policy.

## 5. Request signatures (strict profile)

Ed25519 (RFC 8032), SHA-256, and RFC 9421 signature-base construction are used. This is a deliberately
restricted RFC 9421 profile, not a claim to implement all its algorithms or parsing options.
All signed routes require these headers, even for an empty GET body:

- `Content-Type: application/json`
- `Content-Digest: sha-256=:BASE64(SHA256(exact body bytes)):`
- `X-HG-Key: BASE64URL_NO_PADDING(raw 32-byte Ed25519 public key)`
- `Authorization: HumanGrant anonymous` or `HumanGrant <opaque credential>`
- `Signature-Input` and `Signature` as defined below.

The key ID is `ed25519:` + base64url(SHA256(raw public key)). It is not accepted without a valid
signature. The profile uses one label, `hg`, one component order, and one parameter order:

```text
hg=("@method" "@target-uri" "content-digest" "content-type" "x-hg-key" "authorization");created=1700000000;expires=1700000060;nonce="BASE64URL_RANDOM_24_BYTES";keyid="ed25519:FINGERPRINT";alg="ed25519";tag="humangrant-0.1"
```

`Signature: hg=:BASE64(raw 64-byte signature):`. The signature base has exactly seven lines with LF
separators and no trailing LF. The first six are `"component": value` in the listed order. The last
is `"@signature-params": ` followed by the Signature-Input value after `hg=`. Method is uppercase.
The target URI is the configured origin plus the unmodified request path. A query is rejected.
Every signed header appears exactly once. The profile rejects additional/duplicate parameters,
unknown components, noncanonical base64, or a noncanonical signature input rather than guessing.

A signature lives at most 60 seconds. Creation may be at most 30 seconds in the future. The server
rejects expired signatures. Nonces have at least 192 bits of client randomness. Successful signature
verification reserves `(key_id, nonce)` in SQLite until expiration; replays fail across restarts.
Each retry uses a fresh nonce and signature. Signature verification is proof of private-key possession.
The authorization header is signed, so a signature cannot be moved to a different AI session.
Deterministic public test vectors are in [signature.json](../tests/fixtures/signature.json).

Human authentication challenges are UTF-8 JSON arrays serialized without spaces, in this exact order:
`["HumanGrant human authentication 0.1", origin, request_id, browser_session_hash, challenge_nonce,
expires_at]`. The complete string is returned by the server and signed as exact UTF-8 bytes. Clients
must check the origin against their trusted configuration before signing. A challenge proves account
login only. It does not approve the requested transaction. See [security](../SECURITY.md).

## 6. Grant and credential issuance

A grant records ID, grantor stable account ID, actor identity and public-key ID, client ID, target service,
exact permission/resource pairs, creation/expiry/revocation times, request ID, and audit correlation ID.
The server records consent and grant insertion atomically. Every granted pair must currently be
owned and grantable by this account. Empty grants, unknown actions, and unrequested pairs fail closed.

A claim inserts one unique session per request and stores only SHA-256 of its random 256-bit token.
It changes request phase to succeeded in the same transaction. Concurrent claims cannot issue
multiple sessions. A duplicate claim returns `credential_already_issued` and never returns a token.
If the response or local token file is lost, the token cannot be recovered. The human must revoke that
grant; the AI may request a new authorization only with user approval. Do not report recovered success.
Tokens are reusable with fresh, valid signatures until expiry/revocation; **signatures are not reusable**.
No refresh, delegation, permanent grant, or renewal is defined. Original human cookies and keys never
leave the human client. The AI credential never appears in the state page or mail.

## 7. Polling, failures, and races

The default poll interval is five seconds. A too-early poll returns `slow_down` and `Retry-After`,
increasing the request's interval by five seconds up to 60. Clients wait at least the larger of their
current interval and the server's interval. Network errors use exponential backoff capped at 60
seconds, at most six consecutive failures and no longer than the known request expiry. There is no
automatic new request. On approved, a watch client may claim once, then stop. On success, refusal,
expiry, or cancellation, it stops. A 401/403 also stops instead of repeatedly soliciting permission.

Errors have `{error, message, retry_after_seconds}`. Messages are fixed safe text, not raw database
or transport diagnostics. 400 `invalid_request`; 401 `invalid_signature`, `signature_replay`, or
`invalid_session`; 403 `forbidden`, `csrf_failed`, or `expected_human_mismatch`; 404 `not_found`;
409 `invalid_state`, `credential_already_issued`, or `idempotency_conflict`; 410 `expired`;
413 `body_too_large`; 429 `slow_down` or `rate_limited`; 503 `mail_unavailable`; 500 `internal_error`.
No retries on 400/401/403/404/409/410. For 429 respect Retry-After. For 5xx use bounded backoff,
except credential-claim uncertainty: read status, do not blindly claim or invent a recovered token.

Approve, reject, expiry, cancel, claim, revoke, replay reservation, mail reservation, and protected
business access use SQLite transactions. The implementation uses BEGIN IMMEDIATE for authority-
changing operations. The logical authorization time is sampled inside the transaction. Test clocks
are injected into the library, not exposed by an HTTP endpoint or production request parameter.

## 8. Email privacy and persistent limits

Email is optional. Forwarding a human link works with mail disabled. Development uses a local spool;
test recipients are under reserved `.test`/`.invalid` domains and no network transport is used in tests.
The template fixes sender policy, subject, structure, and all URLs. Purpose is bounded, visibly
untrusted quoted data. CR/LF injection in addresses is rejected. ASCII mailbox input is accepted;
addresses are trimmed and lowercased for conservative limiting (case-distinct mailboxes share limits).

Configurable defaults, not protocol constants: request lifetime 600 seconds; recipient cooldown 60
seconds; recipient 3/hour and 5/day; actor 10/hour; direct source 10/hour; service 100/hour and 500/day.
A service-wide creation limit and actor/source request-creation limits also apply. Recipient counters,
idempotency keys, suppression records, and outbox reservations persist across new request IDs and
restarts. Reserve limits and one operation row atomically before transport. A unique
`(actor_id, idempotency_key)` prevents duplicate sends. Key reuse for different data is a conflict.
Mail never extends request expiry. Queued expired invitations are not sent.

To prevent cross-request mailbox-activity disclosure, the AI sees a generic `accepted` for every
valid submission, including a policy-suppressed submission. This means the send request was accepted,
NOT that mail was queued, transmitted, delivered, read, or linked to any account. Retry information
is based only on this request's own submissions. It must not reveal a mailbox's other traffic or
block decisions. `email_request_status` is `not_requested`, `accepted`, or `unavailable`. Operators
can inspect transport records locally; these are never included in AI state. A delivery confirmation
is not fabricated. Full destination addresses are not included in application/audit logs.

The optional SMTP worker records `transport_accepted`, `failed`, or `delivery_unknown`. A timeout or
disconnect after entering SMTP DATA is ambiguous: the server may have accepted the message. It is
not automatically retried. A crashed `sending` row is also recovered as delivery_unknown. Definitive
failure permits a new, explicitly requested, rate-limited operation; there is no infinite retry loop.
The local spool status is `local_spooled`, never `delivered`. Refusal/block links are read-only on GET;
a user POST is required. Blocking applies to all invitations to that destination because key rotation
must not bypass the recipient's choice. The reference has no self-service unblock endpoint.

## 9. Compatibility and non-goals

JSON schemas and OpenAPI describe this draft only. There is no published package, stable release tag,
third-party client certification, biological-human proof, federated account system, signing-key
rotation, delegated subagents, policy language, multi-region consistency, or full OAuth compatibility.
The Python client is an independent language example. Any runtime/test claim must be backed by the
current [verification record](../docs/verification.md), not by this specification.
